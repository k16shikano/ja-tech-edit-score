# 系統1：編集モデル（SFT + on-policy 選好）

手持ちの推敲ペアで、**下書きを推敲済みへ変換する**ローカル LLM を学習する構想である。
主目標は、フロンティア＋規範スキルの置き換えではない。
いま Qwen で見る問いは次である。

- **推敲変換を、Qwen 程度のモデルに LoRA で後付けできるか**

選好の採点器（pref-bt / pref-sentseq）による勝率は別軸である。
系統3（線型分離の読み取り）と並べて、生成側への埋め込み可能性を測る。

関連：全体方針は [ROADMAP.md](ROADMAP.md)、活性化は [ACTIVATION-STEERING.md](ACTIVATION-STEERING.md)、DOK 手順は [DOK-EDIT-SFT.md](DOK-EDIT-SFT.md)、運用ループは [WORKFLOW.md](WORKFLOW.md)。

## なぜこの形か

ゼロから文章を書く分布 \(P(y)\) を数千件で学ぶのは規模が足りない。
しかし編集モデルが学ぶのは条件付き分布 \(\pi(y \mid x)\)（\(x\)＝下書き、\(y\)＝推敲後）である。
内容の多くは \(x\) が与えるので、モデルが埋めるのは「直し方」に近い不確実性だけになる。
事前学習済みの日本語 LLM が流暢さを既に持つ前提なら、QLoRA 程度の更新で足りることが多い。

Grammarly の CoEdIT（指示付き編集の instruction tuning）も、編集タスクでは小規模モデルでも汎用 LLM を上回ることがある、という先例がある。

## kNN 実例注入との違い

過去に試した系統4（類似ペアをプロンプトへ実例挿入）は、場当たり的な模倣に終わりやすく、ひどい文が出やすかった。
その反省から作ったのが、差分の特徴を言語化した規範スキルである。

系統1は、個別実例を文脈に置くのではなく、全ペア上で勾配を平均する。
表面的な一件への過適合は打ち消され、コーパス全体で一貫する編集傾向が重みに残る、というのが狙いである。

## 理論の要約

### SFT

最尤推定で \(\pi(y \mid x)\) を人間の推敲に寄せる。
複数の正しい直しがあるとき平均に寄りやすく、編集が保守的（ほぼコピー）になることがある。
また、自分の生成分布上での訓練ではないため、生成途中の逸脱を自力で戻しにくい。

### DPO と既存 BT 報酬の関係

KL 正則化付き RLHF の最適ポリシーは

\[
\pi^\*(y \mid x) \propto \pi_{\mathrm{ref}}(y \mid x)\,\exp\bigl(r(x,y)/\beta\bigr)
\]

という閉形式を持つ。
DPO は Bradley-Terry 選好モデル経由で \(r\) を消去し、chosen / rejected ペアだけでポリシーを更新する。
本リポジトリの BT 報酬（`outputs/pref-bt`）は、同じ族の報酬を**明示的に**持つ装置である。

静的に chosen＝人間推敲・rejected＝下書きだけだと、rejected が自明で信号が弱く、かつオフポリシーになりやすい。

### on-policy 化（iterative DPO / RAFT）

1. SFT 済みモデルが温度を上げて N 案を出す
2. BT 報酬で勝敗を付ける（既存の `rank` と同じ裁定）
3. 勝者だけで続ける（RAFT）か、勝者 vs 敗者で DPO する

DeepMind の BOND は Best-of-N 分布そのものの蒸留だが、小規模では RAFT が最短接続である。
フェーズ2は、フェーズ1で後付けが確認できたあとの拡張案として残す。

### 報酬ハッキング

記事デモでは、BT 報酬が短い稿を強く好む傾向が見えた。
iterative 最適化はこのバイアスを増幅しうる。
長さ比の下限、マージン閾値、KL アンカー、held-out での人間抜き取りを最初から入れる。

## 実験計画（外部 GPU 前提）

学習データは非公開原稿由来である。
外部 GPU（高火力 DOK 等、ジョブ終了でコンテナ破棄）では、持ち込んだデータの消去手順をジョブ定義に含める。
成果物に `project_id` やファイルパスを残さない。

### フェーズ0：データ整備（ローカル）

```bash
make edit-sft-export-keeps   # 8310/8311/8312 の keep → 節/空行なし/合流
# レビュー自体は各キューの UI（8310/8311/8312）で完了済み（2026-08-02）
```

詳細と作業記録は [EDIT-SFT-CORPUS.md](EDIT-SFT-CORPUS.md)。

学習本線の要件：

- **単位は節でも hunk でもよい**。短い断片でも、前後と対応が正しければ推敲の教師になる。段落境界の有無は構成学習の制約であり、「壊れた教師」ではない
- **壊れた教師にしないこと**：
  - 比較点はマージ直前（現行 `main` 先端と `edit/...` ではない。マージコミットなら `merge-base(第1親, 第2親)..第2親`、未マージなら `merge-base(mainline, edit)..edit`）
  - 削除塊と挿入塊の無関係な袋詰めなど、対応が取れていないペアを入れない
- 見出しキーが一致しない節は本文類似度で 1 対 1 対応
- chat messages 形式（短い固定指示＋下書き → 推敲後）。規範スキル全文は入れない
- held-out は書籍単位（現状：`what-is-monad` / `computer-arch-revisit` / `ir-system`）
- フィルタ：同一文面・短すぎるもの・sim 過大／過小・対応不良などを除外
- コード／図は `【コード】` / `【図】` に置換。行頭 `★` は削除
- 同一／近傍 draft、推敲連鎖は 1 件に潰す
- **人手で採用したペアだけを学習に使う**（節・hunk とも）。レビュー前 raw や main 先端比較の旧節は足さない

規範スキルとの比較やベンダー FT の出口は、後付けが確認できたあとの議論として残す。
壊れた hunk 教師での「規範に負けたので縮小」は、データ不良下の計測であり、現行の結論にしない（下記履歴）。

## 履歴：実験スキームと、壊れた教師での旧計測

再現や比較のために残す。
**数値そのものは、教師データ不良のため現行の判断根拠にしない。**

### 旧計測で何が悪かったか

1. **hunk の対応破綻**（`git diff --unified=0` の袋詰めなど）  
   隣接する削除塊と挿入塊を 1 ペアにしたため、語彙共有のない対応が混ざった。  
   モデルは「意味を保った推敲」ではなく入力無視を学びうる。  
   **段落が無いこと自体が欠陥ではない。** 欠陥は対応が取れていないことである。  
   退避：`data/edit_sft/archive-2026-07-31-unfiltered/` など。

2. **節の main 先端比較**  
   現行 `main..edit` だと、マージ後に進んだ main が下書き側に混ざる。  
   正しくはマージ直前の fork..edit。  
   退避：`data/archive-section-raw-2026-07-31-main-tip/`。  
   `pref_dataset` 内の旧 `section_pair_mined`（約 438 行）も同系で使わない。

### 副次スキーム：adapter vs base_norms（採点器）

同じベースで次を比べる手順は、再現用に残す。

| 条件 | 中身 |
|------|------|
| `adapter` | ベース＋LoRA。短い指示のみ |
| `base_norms` | ベースのみ。規範全文を前置 |
| `gold` | 人間推敲（参照） |

生成は [DOK-EDIT-SFT.md](DOK-EDIT-SFT.md) 手順4、採点は `scripts/score_edit_sft_eval.py`。

### 旧フェーズ1の数値（hunk 教師・信頼しない）

学習：hunk 系 train 約 5,317 件、Qwen3-8B QLoRA、2 エポック、lr 2e-4、系列長 2048。  
成果物の一例：`outputs/edit-sft/Qwen__Qwen3-8B/`（旧）。

| scorer | wins | losses | ties | win_rate |
|--------|-----:|-------:|-----:|---------:|
| pref-bt | 192 | 523 | 23 | 0.269 |
