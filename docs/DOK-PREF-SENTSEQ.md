# DOK で文列 Transformer 報酬モデル（pref-sentseq）

[ROADMAP.md](ROADMAP.md) の新系統。文書を文単位に分割し、凍結 ruri 埋め込みの列を小さい Transformer に読ませる。
pref-bt（文書全体を 1 ベクトル、LOPO micro 0.975）や pref-ce（cross-encoder）と違い、
**文の順序と段落境界が入力構造として残る** ことを狙う。

## モデル設計

1. **文分割**（`scripts/sentseq_utils.py`、バージョン `v1`）
   - 段落境界: 空行（`\n\n` 以上）
   - 通常段落: 「。」「！」「？」および閉じ括弧（`」』)]`）直後で分割
   - 見出し行（`#` 始まり）、箇条書き行（`-` / `*` / 番号）、コードフェンス内の各行: **1 行 = 1 文**
   - 1 文書あたり最大 128 文で切り詰め

2. **文埋め込み**
   - `cl-nagoya/ruri-v3-30m`（凍結、`text_prefix="文章: "`、`max_seq_length=256`、L2 正規化）
   - ユニーク文を一括エンコードしてキャッシュ

3. **系列**
   - 先頭に学習可能な `[DOC]`（プーリング用）
   - 各文ベクトルを線形射影して `d_model=256` に載せ、学習可能な位置埋め込みを加算
   - **段落境界**: 各段落の先頭文に学習可能な「段落開始」埋め込みを加算（`para_boundary_mode=para_start_embedding`）。
     `[PARA]` トークン挿入は採用していない。

4. **エンコーダ**
   - `nn.TransformerEncoder` 2 層、`nhead=4`、`dim_feedforward=512`、`dropout=0.1`
   - `[DOC]` 位置の出力を文書ベクトルとする

5. **スコア**
   - source / candidate を同じエンコーダで文書ベクトル化
   - pref-bt と同型の点特徴（source、candidate、差、絶対差、コサイン、文字長）→ 線形ヘッド → 1 スカラー
   - Bradley-Terry 損失 `softplus(-(s_chosen - s_rejected))` の平均

## 前提

- `data/pref_dataset.jsonl` と `data/pref_split/` が手元にある
  - hunk のみ: `make train` のデータ生成部
  - **節ペア込み**: `make section-pref-data`
- さくら高火力 DOK と非公開レジストリ

評価の本線は「人間編集が下書きに対し、意味を保ったまま構成・表現が良くなっているか」。
段落結合・過剰分割・順序逆転（`deg-*`）を本線指標にしない（[HARD-EVAL.md](HARD-EVAL.md)）。

## 手順3: 判定

判定の本線は難試験 v1 / v2b / v2c（[HARD-EVAL.md](HARD-EVAL.md)）での pref-bt との比較である。
これには 1 本学習した成果物が要るので、`MODE=train` を先に回してよい（実際その順で実施した）。
「構成だけ」を分離した試験（structure_eval の層別セット、`deg-*` 並べ）は本線に使わない。

LOPO（`MODE=xproject`）は「書籍をまたいだ汎化で pref-bt（micro 0.975）から退行していないか」の裏取りに使う。
ただし LOPO の課題（下書き 対 人間編集）は簡単な多数派に引きずられる（下記「結果」参照）ため、これ単独で採否を決めない。

## 結果1（2026-07-25、MODE=train EPOCHS=20）

学習時の指標（`outputs/pref-sentseq/metrics.json`）: train ペア正解率 0.826、valid ペア正解率 0.839。

### 難試験での pref-bt との比較

| 指標 | pref-bt | pref-sentseq |
|------|--------:|-------------:|
| v1: top-1 正解率（20項目） | 0.45 | **0.80** |
| v1: 総当たり一致率（300組） | 0.830 | **0.877** |
| v2b: 人間編集 > Fable 案の勝率（24項目） | 0.667 | 0.667 |
| v2c: 人間編集 > composer 案の勝率（24項目） | 0.583 | **0.708** |
| 機械案の相対位置の平均（0=コピー、1=人間） | Fable 1.01 / composer 1.53 | **Fable 0.59 / composer 0.42** |

機械負例を一切使わずに、機械推敲案の過大評価が大きく減った。
機械案の相対位置が 0〜1 の間（コピーと人間編集の間）に収まるのは、期待順位「人間 > 機械案 > コピー」と整合する初めてのモデルである。
v2c の勝率 0.708 は、機械負例 456 件＋5 倍重みで再学習した pref-bt 変種（0.625）より高く、線形分離診断の上限（ペア正解率 0.71）とほぼ同じ水準。

留意点: v1 でスコアと文字数の順位相関が 0.79 と高い（pref-bt は 0.50）。v2b/v2c では 0.22〜0.26 と低いので長さだけの説明はできないが、監視は要る。

### valid ペア正解率の内訳（651 ペア、採点で実測）

| 内訳 | pref-bt | pref-sentseq |
|------|--------:|-------------:|
| 全体（651） | 0.980 | 0.846 |
| 単一段落ペア（623、96%） | 0.984 | 0.844 |
| 複数段落ペア（28） | 0.893 | 0.893 |

参考: 長さの特徴（文字数の差など）だけの分類器でも valid 全体で 0.745 当たる。

読み方: pref-bt の 0.98 は、hunk 由来の単一段落ペア（文内の語句の書き換え）での成績が大半である。
段落構成が関わる複数段落ペアでは両者は同点で、pref-sentseq の劣り分は文内の細部（ほぼ同じ 2 文の違いが文ベクトルの差に出にくい）に集中している。
文の細部は pref-bt、並びと構成は pref-sentseq、と得意な水準が住み分けており、二軸併用の運用候補になる。

LOPO 全 fold は未実施（fold ごとの埋め込み再計算を一括化する高速化は実装済み）。

## 結果2（2026-07-26、MODE=train EPOCHS=40）

エポック数だけを 20 → 40 に変えた再学習（`outputs/pref-sentseq-40`）。
このとき `train_pref_sentseq.py` を修正し、metrics.json に「最後のエポック」ではなく
「検証正解率が最良だったエポック（`best_epoch`）」の数値と、エポック数・学習率・バッチサイズを記録するようにした
（保存されるモデルは以前から最良エポックのもの。記録だけが食い違っていた。
20 エポック版の metrics.json にある valid 0.839 は最終エポックの値で、保存モデルの実測は 0.846）。

| 指標 | 20 エポック | 40 エポック |
|------|---:|---:|
| train ペア正解率 | 0.826 | 0.821 |
| valid ペア正解率（651、保存モデルで実測） | 0.846 | 0.857 |
| valid 単一段落（623） | 0.844 | 0.854 |
| valid 複数段落（28） | 0.893 | **0.929** |
| v1 top-1（20項目） | 0.80 | **0.85** |
| v1 総当たり一致率（300組） | 0.877 | **0.893** |
| v2b 人間編集 > Fable 案（24項目） | 0.667 | 0.625 |
| v2c 人間編集 > composer 案（24項目） | 0.708 | 0.625 |

読み方:

- **過学習ではない**。train 正解率（0.821）が valid（0.857）より低いままで、
  検証正解率の最良は最終エポック（best_epoch=40）だった。
- **ただしエポック増の効果は小さい**。20 エポック追加で valid +0.018。
  train 正解率は 0.826 → 0.821 と動かず、学習データすら 0.82 しか当てられない。
  これはエポック不足ではなく、モデルの表現力（d_model=256、2層）か学習の歩幅（学習率）の制約とみる。
- v1 と複数段落は明確に改善、v2b/v2c の勝率は 24 項目中 1〜2 項目分の低下（誤差の範囲内だが、
  「valid への適合が進むと機械案への警戒がわずかに緩む」方向として監視する）。

## 結果3（2026-07-26、容量実験 D_MODEL=512 NUM_LAYERS=4 EPOCHS=40）

容量だけを増やした再学習（`outputs/pref-sentseq-512`、学習率は 1e-4 のまま）。

| 指標 | 256・2層・40ep | 512・4層・40ep |
|------|---:|---:|
| train ペア正解率 | 0.821 | 0.826 |
| valid ペア正解率（best_epoch） | 0.857（ep40） | 0.849（ep26） |
| v1 top-1 | 0.85 | **0.55** |
| v1 総当たり一致率 | 0.893 | **0.723** |
| v2b 人間編集 > Fable 案 | 0.625 | 0.583 |
| v2b 人間編集 > コピー | 0.833 | **0.667** |
| v2c 人間編集 > composer 案 | 0.625 | 0.625 |

判定:

- **壁は容量起因ではない**。容量を約4倍にしても train 正解率は 0.82〜0.83 から動かない。
- **容量増は難試験で明確に有害**。valid（学習と同じ分布）はほぼ同成績のまま、
  分布外の比較（機械案、コピー）だけが崩れた。増えた容量が汎化ではなく
  訓練ペアの個別性の記憶に向かったとみる。採用構成は 256・2層に戻す。
- 残る切り分けは学習率（次: `LR=3e-4`、構成は 256・2層・40ep）。
  ただし容量でも train 0.82 が動かなかったことから、壁の本命は入力表現の限界
  （ほぼ同じ2文の違いが、凍結した文ベクトルの差にほとんど出ない）に移っている。
  その場合、この 0.82 は pref-sentseq の仕様上の上限であり、細部の判別は bt に任せる
  二軸運用の根拠がさらに強まる。

## 結果4（2026-07-26、学習率実験 LR=3e-4、256・2層・EPOCHS=40）

学習率だけを 1e-4 → 3e-4 に上げた再学習（`outputs/pref-sentseq-3e4`）。**現時点の採用モデル**。

| 指標 | lr 1e-4（40ep） | lr 3e-4（40ep） |
|------|---:|---:|
| train ペア正解率 | 0.821 | 0.834 |
| valid ペア正解率（651） | 0.857 | **0.862** |
| valid 単一段落（623） | 0.854 | 0.860 |
| valid 複数段落（28） | 0.929 | 0.893 |
| v1 top-1 | 0.85 | 0.80（1項目差） |
| v1 総当たり一致率 | 0.893 | 0.893 |
| v2b 人間編集 > Fable 案 | 0.625 | **0.708** |
| v2c 人間編集 > composer 案 | 0.625 | **0.708** |
| 機械案の位置が(0,1)内の率（v2b/v2c） | 0.75 | **0.85** |

判定:

- 容量実験と違い、**分布外（機械案・コピー）の挙動を保ったまま valid と難試験の両方が伸びた**。
  lr 1e-4 の 40ep で見えた「valid への適合が進むと機械案への警戒が緩む」傾向も出ていない。
- train 正解率は 0.834 で、壁は 0.82〜0.83 からほぼ動かず。エポック・容量・学習率のどれでも
  大きくは越えられないので、細部判別の上限は入力表現（凍結文ベクトル）由来とほぼ確定。
- best_epoch=40（最終エポックでまだ更新）なので、`EPOCHS=80 LR=3e-4` の余地は残るが、
  1 回あたりの伸びは縮んでおり優先度は低い。次の本命は LOPO（`MODE=xproject EPOCHS=40 LR=3e-4`）。
- 監視点: v1 のスコアと文字数の順位相関が 0.78 と高いまま（v2b/v2c は 0.20〜0.23）。

- **micro 0.905 / macro 0.910**（6,274 ペア）。同一分布の valid 0.862 より高く、

- pref-bt（micro 0.975）との差が大きいのは `eff`（0.981 対 0.842）と `ts-tapl`（0.953 対 0.861）の

- 注意: pref-bt の LOPO レポート（`outputs/eval_bt_xproject.json`）は節ペア追加前の
  データセット（総ペア 5,887）での実施なので、fold 対応の比較は目安。

LOPO でも「細部＝bt、構成と機械案の格付け＝sentseq」の住み分けが崩れないことを確認した。
次は二軸運用の実装（`make check` / Best-of-N への組み込み）。

## 二軸運用の実装（2026-07-26）

- 共通ローダ `scripts/pref_scorer.py` が pref-sentseq を自動判別する
  （`model.pt` があれば sentseq、meta.json の kind が pref-ce なら cross-encoder、他は bt）。
- **Best-of-N（`make rank`）が二軸の入口**。既定で主モデル= `outputs/pref-sentseq-3e4`、
  ゲート= `outputs/pref-bt`。ゲートは「下書きに対する bt マージンが `GATE_MIN_MARGIN`
  （既定 0）未満の候補＝細部が悪化した候補」を失格にし、残りから sentseq スコア最大を選ぶ。
  `GATE_MODEL=`（空）で一軸に戻る。候補が1つでも合否判定として使える。
- 収束判定（`make converge MODE=bt`）は `BT_MODEL=outputs/pref-sentseq-3e4` で sentseq に
  差し替えられる。スコアのスケールがモデルごとに違うので `MIN_IMPROVEMENT` は合わせて選ぶ。
- `make check`（hunk 単位の git diff 採点）は細部軸の道具なので pref-static / pref-bt のまま。
  文書・節単位の二軸判定は rank / converge を使う。

## 合格閾値の較正（2026-07-26）

「人間の編集に十分近くなるまで生成 → 推敲のループを回す」運用のため、
検証セット 651 ペアで人間編集が下書きから稼ぐマージンの分布を測った
（`make calibrate-margins` → `outputs/acceptance_margin_calibration.json`）。

マージンには 2 つの定義があり、区別が必要である。

- **pair 基準**: margin = s(source_text, 人間編集) − s(source_text, 下書き)。
  学習・検証と同じ形で、共通の基準に対する 2 候補の差。
- **self 基準**: margin = s(下書き, 人間編集) − s(下書き, 下書き)。
  運用時（`make rank` のコピー比較、`make revise`、採点 Web サービス）の定義。
  基準と候補が同一という学習にない入力を含む。

| パーセンタイル | sentseq (pair) | sentseq (self) | bt (pair) | bt (self) |
|---|---:|---:|---:|---:|
| p5 | −0.31 | 0.03 | 0.45 | 2.75 |
| p25 | 0.09 | 0.38 | 5.04 | 10.88 |
| p50（中央値） | 1.89 | 3.74 | 18.59 | 25.91 |
| p75 | 10.89 | 13.19 | 34.78 | 42.37 |
| マージン正の率 | 0.862 | **1.000** | 0.980 | **1.000** |

### self 基準の「変更しただけで加点」の偏り

self 基準では人間編集の 651 ペア全件が正のマージンになる。さらに、
方向を逆にしても（人間編集を基準に下書きを候補にしても）12/12 ペアで正であり、
冗長な言い回しを機械的に挿入した劣化版でも sentseq で一律 +4.3、bt で +2〜+7 が付いた。
つまり **s(x, x) が学習分布の外で低く出るため、どんな変更にも正のマージンが付く**。
劣化版の +4.3 は人間編集の self 中央値 3.74 を超えており、
**self 基準の正のマージンは改善の証明にならない**。

使い方の目安:

- **合格ライン（主軸）**: 運用は self 基準なので、閾値も self 分布から選ぶ。
  既定は中央値 3.7（`make revise MIN_MARGIN=3.7`）。ただし上記の偏りにより、
  この閾値は「人間編集の分布上の位置」の目安であって合否の保証ではない。
  候補同士の順位付け（Best-of-N）は 2 候補とも基準と異なるので偏りの影響が小さく、
  こちらが本来の使い方である。
- **ゲート（bt）**: 既定の 0（悪化していない）。self 基準の偏りぶん（+2〜+7）を
  見込むなら p25 の 10.9 まで上げる。
- 注意: マージンは編集量にも比例する（小さな編集は正しくても小さい）。
  軽微な推敲しか要らない節では p25 側を使う。

## 採点 Web サービス（2026-07-26）

下書きと推敲を貼り付けて二軸のマージンを見るローカル Web サービス
（`make serve` → http://127.0.0.1:8300、`scripts/score_server.py` + `web/index.html`）。

- 点数は self 基準のマージン。上記の偏りがあるため、UI は絶対値ではなく
  self 分布上の百分位（ゲージ）を主表示にしている。
- 合否判定は主軸 ≥ 3.7（self 中央値）かつゲート ≥ 0 の暫定ルール。
- 128 文超（sentseq の切り詰め）や 1500 字超（bt の最大系列長）には警告を出す。
- 単独の文章への絶対採点は提供しない。Bradley-Terry 学習は同一下書き内の
  スコア差しか拘束しないため、異なる文書間の点数比較は正当化できない。

## アンカー付きペアの実験（2026-07-26、不採用）

self 基準の偏りを学習データ側で直す試み。実ペアの役割を組み替えて、
「基準=下書きで人間編集 ≻ コピー」（anchor-fwd）と「基準=人間編集で
コピー ≻ 下書き」（anchor-rev）の 2 種 9,984 行を train 側だけに追加した
（`scripts/build_anchor_pairs.py` → `data/pref_split_anchor/`）。

結果は不採用（`scripts/exp_anchor_head.py` → `outputs/anchor-exp/report.json`、
モデルは `outputs/pref-bt-anchor`）。

| 指標 | 線形ヘッド | MLP ヘッド（隠れ256） |
|---|---:|---:|
| 検証ペア正解率 | 0.811 | 0.816 |
| 順方向（下書き→編集）が正 | 0.742 | 0.747 |
| 逆方向（編集→下書き）が負 | 0.633 | 0.771 |
| 劣化版が負 | 0.500 | 0.167 |

- 検証正解率がアンカーなしの 0.98 から 0.82 前後に落ち、マージン全体が
  0 付近に圧縮される。逆方向は MLP で 0.77 まで改善するが、劣化版には
  どちらのヘッドも正のマージンを与え続ける。
- 診断: 学習に「悪い変更」が一度も現れないことが原因。アンカーは
  「コピーは実編集に負ける」「良い版からの後退はコピーに負ける」までしか
  教えられず、「任意の変更が悪いこともある」は教えられない。
  これはヘッドの表現力（線形か非線形か）では解決しない。
- 帰結: 方向感度（入れ替えたら負になる）を得るには、悪い変更の負例
  （機械劣化、または機械推敲案の中間ランク付け）を学習に入れる必要がある。
  合成負例の追加は過去に効果が薄いと判断した経緯があるため、採否は別途判断。

## 推敲ループの 1 コマンド化（2026-07-26）

生成 → 二軸判定 → 反復 → 打ち切りを `make revise` で回せる（`scripts/revise_loop.py`）。

```bash
export CURSOR_API_KEY=...
make revise FILE=下書き.md [N=3] [MAX_ITERS=3] [MIN_MARGIN=3.7] [GEN_MODEL=composer-2.5]
```

- **入力ファイルは見出し単位の節に自動分割**され、節ごとにループが回り、
  最後に全体が組み直される。採点モデルの学習データが節単位（最大83文）なので、
  これが正しい粒度である。`MIN_SECTION_CHARS`（既定 200）未満の節はそのまま通す。
  `ONLY_SECTIONS=見出しの部分一致` で節を絞れる。
- 各反復で Cursor SDK により推敲案を N 件生成（プロンプトは素の推敲指示と、
  段落の切り方・並びの見直しを指示する2種を交互に使う）。
- 生成プロンプトには既定で執筆規範スキル（`japanese-tech-writing` と
  `cognitive-rhythm-writing`、`~/.cursor/skills` から読み込み、計約1.4万字）を
  規範として同梱する。`SKILLS=none` で無効化、`SKILLS=名前,名前` で差し替え。
- pref-sentseq のマージン（**元の節基準**）で順位付けし、pref-bt の
  マージンが `GATE_MIN_MARGIN`（既定 0）未満の案は失格。
- 節ごとの終了条件は4つ: 合格（マージン ≥ `MIN_MARGIN`、既定 3.7 = self 基準の
  人間編集中央値）、改善停止（1反復の伸びが 0.1 未満）、全候補失格、反復上限。
- 推敲版は `<file>.revised.md`、節ごとの経過は `<file>.revise-report.json` に出る。
  全処理節が合格に届かなければ exit code 2。
- 注意: マージンは self 基準なので「変更しただけで加点」の偏りが乗る
  （上の較正の節を参照）。合格は「人間編集の分布上の位置」の目安であり、
  改善の保証ではない。候補間の順位付けが本来の強みで、合否はゲートと
  人間の確認で補う。編集量にも比例するため、仕上げ段階の原稿には
  `MIN_MARGIN=0.4`（p25）を使う。

## 実験の進め方（変数を1つずつ動かす）

train 正解率 0.82 の壁の原因を切り分けるため、1 回の実験で動かす変数は 1 つにする。

1. **エポック数**（実施済み: 20 → 40）: 学習データを何周するか。
   検証正解率が最良のエポックのモデルが保存されるので、増やすこと自体に害はない。
   結果: 効果は小さく、壁の原因はエポックではない。
2. **容量**（実施済み: `D_MODEL=512 NUM_LAYERS=4 EPOCHS=40`）: Transformer の幅（d_model）と層数。
   モデルが表現できる関数の複雑さを決める。
   結果: train 正解率は動かず、難試験は退行（結果3）。壁は容量ではない。
3. **学習率**（実施済み: `LR=3e-4`、構成は 256・2層・40ep。結果4のとおり採用）: 重みの更新式
   「新しい重み = 現在の重み − 学習率 × 損失の勾配」に掛かる、一歩の幅を決める乗数。
   小さすぎると収束が遅く、大きすぎると発散する。最適化手法 AdamW はパラメータごとに歩幅を
   自動調整するが、その全体に掛かる基準がこの値。容量を増やしても train 正解率が
   0.82 付近から動かないなら、歩幅が小さくて最適化が進んでいない疑いに移る。

## pref-bt との併用の実測（2026-07-26、20 エポック版で計測）

「1 本のスコアに合成するか、二軸で併用するか」を、両モデルの既存スコアの線形合成
（各モデルのスコアを標準化し、重み α を sentseq に、1−α を bt に掛けて加算）で実測した。

- **難試験（v1 / v2b / v2c）では α=1（sentseq 単独）が全指標で最良**。中間の α は
  v2c の「機械案の相対位置」の利点を大きく削る（α=0.5 で中央値 0.10 → 0.34）。
- **valid では α=0.25〜0.5 がわずかに最良**（0.980 → 0.982、複数段落 0.893 → 0.929）。
- valid 651 ペアの誤りの内訳: bt のみ正解 91、sentseq のみ正解 4、両方不正解 9。
  項目レベルでは sentseq は bt にほぼ包含されて劣る。相補性は項目単位ではなく**課題の種類単位**
  （細部の判別＝bt、機械案の格付け＝sentseq）にある。

結論: 固定重みの合成スカラーはどの α でも両方の課題で最良にならず、難試験 20〜24 項目で
α を調整するのは過学習になる。当面は**二軸運用**（生成候補のランキングと絶対スコアは sentseq、
「下書きに対して細部が悪化していないか」の補助ゲートに bt）とし、
sentseq の改良（容量・学習率）と LOPO の後に一本化を再判定する。

ローカル:

```bash
make eval-sentseq-xproject ONLY_PROJECTS=ir-system EPOCHS=2
make eval-sentseq-xproject
make train-sentseq
make hard-eval-score INPUT=data/hard_eval/bases_v1_labeled.jsonl SCORER=sentseq MODEL=outputs/pref-sentseq
```
