# 段落遷移モデル

## 目的

完成稿の段落列から、隣接する2段落のつながりの自然さを学習する分類器を作る。下書きの段落境界ごとに遷移スコアを出し、つながりの悪い箇所を指摘する用途を想定する。

既存の選好モデル（pref-bt、pref-ce）は語句レベルの改善は判別できるが、段落の並びや節内のつながりまでは判別できない。段落境界専用の信号を別モデルで取る。

## 負例の設計

正例は同一節内の隣接段落対 `(A, B)` である。

負例は同一書籍（`project_id`）内の非隣接段落対から取る。同一節内では段落インデックス差が2以上の組、別節の組を混ぜ、正例と同数をランダムサンプリングする（seed 固定）。

機械的なシャッフル改悪（段落結合、一文ごとの過剰分割、段落順の逆転など）は使わない。`.cursor/rules/preference-eval-goal.mdc` にある通り、それらは本線の評価・学習の対象外である。実在する非隣接段落は、話題が離れた自然な対照になりうる。

## 学習データ

- 入力 manifest: `data/section_mining_manifest.json`
- 各リポジトリの edit ブランチ（`origin/` フォールバック付き）の Markdown から抽出
- held-out 9 リポジトリ（`scripts/batch_mine_heldout_sections.sh` の REPOS）は学習に含めない
- 出力: `data/paragraph_transitions.jsonl`

## モデル

- 埋め込み: `cl-nagoya/ruri-v3-30m`（重みは更新しない）
- 特徴: `[emb_a, emb_b, emb_a*emb_b, |emb_a - emb_b|]`
- 分類器: ロジスティック回帰（StandardScaler 付き）
- 検証: leave-one-project-out（LOPO）

## 実行手順

```bash
make transition-data    # 段落対抽出
make train-transition   # 学習 + LOPO レポート
make eval-transition    # held-out 節ペアで編集前後を採点
```

成果物:

- `outputs/paragraph-transition/model.joblib`
- `outputs/paragraph-transition/metrics.json`
- `outputs/paragraph-transition/eval_on_edits.json`
- `outputs/paragraph-transition/eval_on_edits.md`

## 編集前後検証の読み方

入力は `data/examples.section.heldout.jsonl`（下書き `source_text` と人間編集 `edited_text`）。

各節について、**学習時と同じ段落フィルタ**（コードブロック・表・マーカー・見出しのみ・短段落の除外）を通した段落列の隣接境界ごとに遷移スコア（隣接らしさの確率）を出し、文書スコアとして境界スコアの平均と最小を使う。

集計は次の2群に分ける。

- **(a) 段落構成が変わったペア**: 段落数が変化、または段落列が変化
- **(b) 全ペア**

指標は「編集後スコア > 下書きスコア」の勝率、スコア差の平均・中央値。

### 境界数の偏り

最小値指標は、境界数が多い文書ほど機械的に下がりやすい。下書きと編集後で境界数が異なるペアでは、最小値の比較が不公平になりうる。held-out 112 節ペアでは、採点可能 106 件のうち境界数同じ 60 件・異なる 46 件。レポートには境界数同じペアに絞った勝率も載せる。

### 最新結果（held-out 112 節ペア）

| グループ | 指標 | 修正前（フィルタ未適用） | 修正後（全ペア） | 修正後（境界数同じ） |
|---|---|---:|---:|---:|
| (a) 構成変化 | 平均 | 46.6% | 42.0% | 44.4% |
| (a) 構成変化 | 最小 | 29.1% | 28.0% | 31.5% |
| (b) 全ペア | 平均 | 45.3% | 39.6% | 40.0% |
| (b) 全ペア | 最小 | 28.3% | 26.4% | 28.3% |

修正前は `\n\n` 分割のみで採点していた。修正後は学習時と同じフィルタを適用した。いずれも勝率は 50% を下回る。

隣接性の学習が話題連続性しか拾っていない場合、編集前後でスコアは動きにくい。勝率が低くても、そのまま報告する。動いたかどうかの判定がこの検証の目的である。
