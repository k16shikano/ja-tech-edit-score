## 用語

本書で使う言葉は次の意味に固定する。これ以外の略語・符丁は使わない。

| 言葉 | 意味 |
|------|------|
| 推敲前後ペア | 人がレビューして「正しい推敲の実例」と確定した、下書きと推敲後の対。全 1976 件 |
| 節ペア | 推敲前後ペアのうち、段落境界（空行）を含むもの。379 件 |
| 断片ペア | 推敲前後ペアのうち、空行を含まない短いもの。1597 件 |

| 評価器 | 下書きと候補文を受け取り、良し悪しの点数を返すモデル。節ペアで学習する文列型と、断片ペアで学習する Bradley-Terry 型の 2 つ。工程 3 で新しい分割の学習側だけを使って学び直す（既存の `outputs/pref-sentseq-keep` / `outputs/pref-bt-keep` は書籍単位の分割で学習したもの） |
| 推敲モデル | Qwen3-8B に LoRA（低ランクの追加重み）を載せた生成モデル。工程 3 で新しい分割の学習側だけを使って **SFT** で学び直す（既存の `outputs/Qwen__Qwen3-8B-revised-2000` は書籍単位の分割で学習したもの）。この段階では gold の文面再現や選好の獲得を目指さない |
| 素のモデル | LoRA を載せない Qwen3-8B |
| 指示文 | 学習データの user 発話と、生成の両方で同一に使う指示。確定文は次のとおり（工程 3 で採用、判定実施の知見で改訂）。「次の下書きを、意味を保ったまま日本語の技術文書として推敲せよ。／行頭の # で始まる見出しと、【図】・【コード】などの置き場所を示す要素は原稿の構成要素である。推敲の一部として位置を動かすのはよいが、省いてはならない。／文体（ですます調・である調）は下書きのまま保て。変えてはならない。／出力は推敲後の本文のみ。前置き・後書き・変更点の説明・「このようにすると…」のようなメタ文言は書くな。」構成要素の保持と文体の保持を足したのは、初回の判定で素のモデルの生成に見出し欠落（75%）や文体の変更が頻発し、比較が「欠落・逸脱を弾く」作業になって編集の質を測れなかったため |
| 貪欲生成 | 各ステップで最も確率の高い語だけを選ぶ生成。同じ入力なら毎回同じ出力になる |
| サンプリング生成 | 確率に従って語を選ぶ生成（温度 0.7、top_p 0.9、シード固定）。同じ入力から複数の案を出せる |
| Best-of-N | 同一入力から N 案を生成し、報酬モデル（評価器）で順位を付けて最良の 1 本を採る。実装は `scripts/rank_pref_bt.py`（`make rank`）。工程 5 の比較 4・5 は N=8 の Best-of-N に相当 |
| 中間 | 同じ下書きから出した LLM の推敲。質の評価器の尺度の真ん中に置く文。Composer（既定 `composer-2.5`）が、工程 4 と同じ指示文で 1 本出す。人が下書きより劣化していないと付けたものだけを三つ組みに入れる。推敲モデル（Qwen にアダプターを載せたもの）の生成は、中間にしない |
| 三つ組み | 同じ下書きについての三つの選好対。人間の推敲 ＞ 下書き、人間の推敲 ＞ 生成、生成 ＞ 下書き。生成が下書きより劣化していると人が付けた件は、生成を含む対を作らない |

## 目的

1. **評価器の性能の測定**: いまの評価器が人間の判断とどれだけ一致するかを、初めて直接測る。「評価器の性能をどう決めるか」自体が未解決の問題であり、この測定はその試行錯誤の一部である。事前の合格ラインは置かない。
2. **推敲モデルの成否判定**: 条件を揃えた比較で、SFT によって「指示に従った推敲」が載ったかどうかを判定する。判定の根拠は人手のブラインド判定であり、評価器の点数でも gold との文字列一致でもない。選好に沿った生成の強化は、質の評価器が独立した人手判定（8d）を通ったあとで行う（本計画の SFT 段階の目標ではない）。強化の手段は **DPO 等の on-policy 選好学習**と、**Best-of-N**（複数候補を報酬モデルで順位付けして最良を採る）の両方を残す。DPO で方針を更新し、同じ報酬モデルを Best-of-N の裁定にも使う、という組み合わせも想定する。

## これまでの実験の何が駄目だったか

1. 検証ペアでの生成比較が「推敲モデル」対「規範全文を前置した素のモデル」だった。指示文が違うので、LoRA の効果の比較になっていない。
2. 生成が貪欲のみだった。貪欲は分布の最頻の 1 本しか見ないので、「分布の中に良い推敲があるか」を測れない。
3. 学習と検証の分け方が書籍単位だった。ペア数の書籍分布に大きな偏りがあるので、検証側が特定の書籍の文体・分量に寄る。この課題で主張したいのは個々の推敲の質であって、書籍をまたぐ汎化ではないから、書籍単位で分ける必要も合理性もない。ペア単位の乱択に変える。

評価器の点数はこれまで「生成が変化したか」の観察に使っただけで、成否判定には使っていない。
考察の中でそれを成否のように扱った記述があったが、それは解釈の誤りであって、実験の手順の誤りではない。
本計画では、人手判定を根拠の位置に置くことで、この混同が起きない形にする。

## 判定基準

### 推敲モデルの成否（結果を見る前に固定する）

人手のブラインド判定（工程 6）で測る。対象 60 件。

- **成立**: 「推敲モデルの貪欲生成」が「素のモデルの貪欲生成」より良いと判定された割合が 0.6 以上（60 件中 36 件以上）
- 参考値として「下書きより良い」割合も出す（0.6 以上を期待値とする）
- 下書きとの文字列類似度（コピー率）は記録するが、成否の基準にはしない

### このブラインド判定が測っているもの（判定実施中の再定義。数値基準は動かさない）

判定を始めて分かった事実として、多くのペアには「良い推敲」が提示されていない。
候補は「やってはいけない編集（見出しの欠落・内容の破壊・文体の変更）」か「許容できる出力（無編集・無害な言い換え）」のどちらかであることが多く、判定は「良いほうを選ぶ」ではなく「悪いほうを弾く」作業になっている。
したがって、この判定の結果を「良いものを選んだ結果」とみなして実験や評価を組み立ててはならない。
各比較の勝率が何の主張に使えるかを、次のとおり限定する。

- **比較 3（base 対 adapter）**: 「どちらが許容できない出力を出しにくいか」の測定。成立基準（0.6）はこの値のまま動かさないが、成立しても主張できるのは「LoRA で出力が壊れにくくなった」まで。「推敲の質が上がった」の根拠にはしない
- **比較 2・4（下書き 対 生成）**: 生成側の勝ちだけが「何もしないより良い編集を作れた」ことを意味する。**推敲能力の直接の証拠はここで見る**。無編集は同等にしかならないので、この勝率を押し上げられない
- **比較 5（人間の推敲 対 選抜）**: 人間との距離。互角（0.5 付近）に近づくことが推敲能力の強い証拠
- **比較 6（人間の推敲 対 下書き）**: 判定者の基準確認。人間の推敲が高い割合で勝たないなら、判定か対象選定に問題がある

判定の相対選択（ボタン）は「採用するならどちらがましか」であって「どちらが良い編集か」ではない。
「A に致命的欠陥、B は下書きとの事実上の差分なし」のような、どちらも良くないペアがあるためである。
そこで判定ごとに、相対選択とは別に各候補の絶対評価を 2 つのチェックで記録する。

- **致命的な欠落・破壊がある**（見出し・【図】【コード】の欠落、内容の破壊、文体〔ですます調・である調〕の変更など）
- **下書きとの事実上の差分なし**（完全一致でなくても、言い換え程度で編集と呼べないもの）

集計では勝ちを次の三つに分類する。

- **失格勝ち**: 相手に致命的欠陥がある勝ち
- **無編集勝ち**: 勝った側が事実上の差分なしの勝ち
- **品質勝ち**: 上のどちらでもない勝ち。勝った側が編集として成立している

学習の成果は、比較 3 の勝率 1 本ではなく、次の三つの率を並べて判断する。

- **破壊率**: 致命的な欠落・破壊のある出力の割合
- **無編集率**: 下書きとの事実上の差分がない出力の割合。完全一致は機械計測でも出し、人手チェックと併記する
- **改善率**: 比較 2 で生成側が**品質勝ち**した割合

「推敲能力が載った」と言えるのは改善率を主張の中心にできるときだけで、破壊率の低さと無編集の多さで比較 3 に勝っただけなら「安全側に倒すことを学んだ」と記す。

### 評価器の測定（合格ラインは置かない）

評価器に事前の合否基準を置けるだけの知見がまだない。v2 / v2b / v2c の勝率は評価器の採否に使わない。
そこで本計画では、同じ人手判定データを使って次を**測定**し、結果を評価器の現在地として記録する。

- 比較の種類ごと（人間の推敲 対 下書き／人間の推敲 対 生成案／下書き 対 生成案／生成案どうし）の、人の判定との一致率
- 一致率の分母は `choice` が `a` / `b` の比較可能件数。`tie`（同等）は件数として別掲し、一致率には入れない
- 候補に致命的欠落・破壊チェック（`a_broken` / `b_broken`）が付いていても、人手が A/B を選んでいれば比較可能に含める。欠陥報告件数は参考列として併記する
- 候補の点数と文字数の順位相関（長さに釣られていないかの確認）
- 人と食い違った対の内訳（どんな推敲で外すのか）

これは評価器を合否で切る工程ではなく、「評価器の性能をどう測ればよいか」への最初の直接データを得る工程である。
工程の中で評価器に候補選抜をさせるのも（工程 5 の比較 4・5）、選抜の当たり外れ自体を人手判定で測るためであり、評価器を信頼している前提ではない。

人手判定データは、一度取れば設定違いの評価器を何通りでも追加の人手費用なしに測れる（判定済みの対を採点し直すだけでよい）。
評価器の学習設定（埋め込みモデル、学習率、swap 増強の有無など）は最適と分かっているわけではないので、その選択はこの測定を物差しにして行う。

## 工程

### 工程 1: ペア単位の分割の作り直しと、判定対象 60 件の選定（手元、スクリプト作成）

全 1976 件を、書籍に関係なくペア単位で分割し直す。

- シードを固定した乱択。節ペアと断片ペアの比率を保つ層化にし、検証側を 260 件程度にする
- 同じ分割から、SFT 用データ（`data/edit_sft_all`）と評価器用データ（`data/pref_keep_split_hunk` / `data/pref_keep_split_section`）の両方を作り直す。分割が食い違うと、評価器が検証ペアを学習済みという漏れが起きるため
- 検証側から、人手判定に使う 60 件を選ぶ。節ペアを優先し（構成を含む推敲を見たいため）、極端に短いもの（100 文字未満）は除く。これもシード固定の乱択とし、選定スクリプトと結果を保存する

成果物: 分割を作り直した上記データ、`scripts/select_blind_items.py`、`data/blind_eval/items.jsonl`（対象の id 一覧と下書き・人間の推敲）

### 工程 2: 生成スクリプトの拡張（手元）

`scripts/generate_edit_sft.py` はいま、貪欲生成 1 本しか出せない。次を追加する。

- `--num-samples N`: サンプリング生成を N 本出す（0 なら従来どおり貪欲 1 本）
- `--temperature` / `--top-p` / `--seed`
- `--ids-file`: 指定した id のペアだけを対象にする（工程 1 の 60 件に絞るため）
- 出力レコードに生成方式（貪欲かサンプリングか）、サンプル番号、生成パラメタを記録する

起動スクリプト `scripts/dok_edit_sft_eval.sh` と `Dockerfile.edit-sft-eval` も合わせて更新する
（モード既定を `base adapter` にする。`base` は指示文で動く素のモデル、`adapter` は同じ指示文で動く推敲モデル。規範全文を前置するモードは今回使わない）。

成果物: 更新済みスクリプト、再ビルドした Docker イメージ（`ja-tech-edit.sakuracr.jp/edit-sft-eval:latest`）

### 工程 3: 推敲モデルと評価器の学び直し（GPU と手元）

工程 1 の新しい分割の学習側だけを使って、三つを学び直す。

これまでの学習設定が最適だった根拠はないので、旧設定の踏襲を目的にしない。
ただし推敲モデルは、設定違いを比べるたびに人手判定の費用がかかる。そこで本計画では 1 設定に固定し、既知の欠陥だけをこの学び直しで直す。設定の探索は工程 8 以降で、同じ判定手順を物差しにして行う。

- **指示文の確定**: 学習データの user 発話と工程 4 の生成の両方に、同一の指示文を使う。確定した指示文は用語表のとおり（本文以外の出力禁止を含む）。`scripts/export_edit_sft.py` の `INSTRUCTION` が正本で、SFT データ再生成・バッチ生成・対話検証がこれを共有する
- **形式の一致の確認**: Qwen3 の思考モードは生成側では無効が既定。学習時は `train_edit_sft.py` が `enable_thinking=False` でチャットテンプレートを直列化し、生成側と同じ形に揃える
- **推敲モデル**: 上記の指示文で LoRA を **SFT** する。1 回目（2 エポック）では無編集率 23%・`sim_median`（下書き↔生成）0.98 と、ほぼ下書きコピーだった。6 エポックに増やし、チェックポイント毎に少数の貪欲生成の機械計測（無編集率・構成要素の保持・文中断）で使用 checkpoint を選ぶ。選定は機械ゲートのみ（人手判定・gold 一致は使わない）。DOK で 1 ジョブ。出力は `outputs/Qwen__Qwen3-8B-pairsplit-v2`
- **評価器 2 つ**: `make train-bt-keep` / `make train-sentseq-keep` を作り直したデータで実行する。小さいモデルなので短時間で終わる。これも現行設定を出発点とするだけで、設定違いの比較は人手判定データが取れた後に工程 7 の測定で行う

成果物: 確定した指示文（用語表）、新しい LoRA と評価器 2 つ。以後の工程はすべてこれらを使う

### 工程 4: GPU での生成（さくら高火力 DOK、1 ジョブ）

工程 3 で確定した指示文と同一のデコード条件で、素のモデルと推敲モデルの両方から生成する。

| 生成 | 対象 | 本数 |
|------|------|------|
| 貪欲 | 検証ペア全部（260 件程度）× 2 モデル | 約 520 本 |
| サンプリング | 工程 1 の 60 件 × 推敲モデルのみ × 8 本 | 480 本 |

1 回目に生成した base のサンプル 480 本はどの比較ペアにも使われなかったので、サンプリングは推敲モデルだけにする。既定は **V100**（4bit・短い指示の `base` / `adapter` 生成。B 学習と同条件で VRAM は足りる）。約 1,000 本の逐次生成で **半日を超える**見込みのとき、または OOM のときだけ H100。H100 は秒単価が約 17 倍で、**待ち時間短縮以外**（生成品質・切り詰め解消など）には効かない。エポック選定の再計測（B'、180 本）は [DOK-PLAN.md](DOK-PLAN.md) のとおり V100 で足りる。

生成の最後に機械計測（`scripts/generation_integrity.py`）を出す。見るのは無編集率・文中断率・見出しと【図】【コード】の保持率だけ。**gold との類似度や選好一致は見ない。** 比較実験として成立する生成かを確認してから工程 6 の人手判定に進む。

成果物: `outputs/edit-sft-eval-v3/` に `base_greedy.jsonl`、`adapter_greedy.jsonl`、`adapter_samples.jsonl`、`integrity_summary.json`

### 工程 5: ブラインド判定 Web アプリの開発（手元）

人が候補文を、出所を知らずに比較するためのローカル Web アプリを作る。

**構成**: FastAPI のサーバ（`scripts/blind_judge_server.py`）と 1 枚の HTML（`web/blind_judge.html`）。`make blind-judge` で起動する。

**判定ペアの構成**（60 件それぞれに 6 対、計 360 判定）:

| # | 比較 | 何を知るためか |
|---|------|----------------|
| 1 | 下書き 対 素のモデルの貪欲生成 | 素のモデルだけでどこまで直るか |
| 2 | 下書き 対 推敲モデルの貪欲生成 | 推敲モデルが下書きを改善するか |
| 3 | 素のモデル 対 推敲モデル（ともに貪欲） | LoRA の効果そのもの（成否判定の基準） |
| 4 | 下書き 対 推敲モデルのサンプル 8 本から選んだ 1 本 | 候補選抜込みで実用になるか |
| 5 | 人間の推敲 対 推敲モデルのサンプル選抜 1 本 | 人間との距離 |
| 6 | 人間の推敲 対 下書き | 判定者の基準確認と、評価器の一致率測定 |

**機能要件**:

- 事前にペア一覧を作って保存する（`scripts/build_blind_pairs.py` → `data/blind_eval/pairs.jsonl`）。左右の割り付けと出題順はシード付き乱数で決め、対応表はサーバ側だけが持つ
- 比較 4・5 の候補選抜は、まず機械フィルタ（見出しと【図】【コード】の本数を保ったサンプルだけ残す）を通し、残りを評価器で順位付けする。1 本も残らなければ貪欲生成で代替する。1 回目に評価器の選抜が欠損入りサンプルを 60 件中 6 件で選んだため（健全なサンプルは平均 7.3 本あった）、整合性の検査は評価器に任せない
- 画面には元の下書き（文脈）と、匿名の候補 A / B を並べて表示する
- ボタンは「A のほうがまし」「B のほうがまし」「同等」の 3 つ（採用するならどちらか、の相対選択）。任意でコメント欄
- 各候補に「致命的な欠落・破壊がある」「下書きとの事実上の差分なし」のチェックを置き、判定と一緒に保存する（勝ちを失格勝ち・無編集勝ち・品質勝ちに分類するため）
- 判定は 1 件ごとに `data/blind_eval/judgments.jsonl` へ追記し、中断・再開できる
- 進捗（残り件数）を表示する

判定 1 件 30〜60 秒として、全 360 件で 3〜6 時間。負担が大きければ対象を 40 件（240 判定）に減らしてよい。減らす場合も基準の割合は変えない。

成果物: 上記スクリプト・HTML・`make blind-judge` ターゲット

### 工程 6: 人手判定の実施（判定者の作業）

工程 5 のアプリで 360 判定を行う。分割実施でよい。

成果物: `data/blind_eval/judgments.jsonl`

### 工程 7: 集計（手元、スクリプト作成）

- 推敲モデル: 三つの率（破壊率・無編集率・改善率）を中心に置き、比較 3 の勝率と二項検定、比較 4・5 の勝率、長さ比を併記
- 勝ちの内訳: 全比較種別で、勝ちを失格勝ち・無編集勝ち・品質勝ちに分類し、出所ごとの破壊率・無編集率と併記
- 評価器の測定: 全判定ペアを両評価器で採点し、比較の種類ごとの一致率（`a`/`b` 選択のみ。`tie` は件数別掲）・欠陥報告件数（参考）・文字数相関・食い違った対の内訳を出す
- 結果は `docs/RESULTS.md` に、本書の基準（推敲モデル）および測定項目（評価器）と並べて記録する

成果物: `scripts/analyze_blind_judgments.py`、`docs/RESULTS.md`

### 工程 8: 質の評価器の教師と学び直し

質の評価器が再現するのは、下書きより人間の推敲がよいか、である。尺度の真ん中に置く文は、同じ下書きから出した LLM の推敲で、人が「下書きより劣化していない」と確かめたものに限る。工程 6 の 360 件の相対選択（ましなほう）は、この教師にしない。選抜 1 本も入れない。

BT 三つ組み文列型の学習と工程 6 採点は済み。setwise 修正版（full-order）と human-top 版の DOK 学習も済み。v2b / v2c での採点記録は [RESULTS.md](RESULTS.md) §8・§9 に残すが、評価器の採否には使わない。2026-08-14 の旧 DOK 成果物（architecture=`joint_transformer_on_sentence_tokens`）は候補同値崩壊のため不採用だった。8a–8c は閉じた実験の記録である。

評価器の目的は、同一下書きについて人間の推敲を最良に置くことである。各生成モデルの公平な優劣を測るものではない。教師の中間は Composer 固定でよい（Composer だけで学ぶことが目的を妨げない）。

中間の生成は Composer（既定 `composer-2.5`）とする。推敲モデル（Qwen にアダプターを載せたもの）の日本語より、手元で出しやすく一定の質があるためである。指示文は工程 4 の評価生成と同一である。人間の推敲はプロンプトに見せない。人が付けるのは、生成が下書きより劣化していないかだけである。人間の推敲とは比べない。

**新しい評価器が、独立した人手データで検証されるまで、DPO / Best-of-N の教師・裁定には使わない。**

#### 8-mid. 節ペアの三つ組み（BT 文列型・setwise 修正版とも学習済み。v2 は評価器の採否に使わない）

節ペア 379 件の下書きそれぞれに、上記の指示文で Composer 推敲を 1 本出した。人が下書きと生成だけを見て、劣化していないかを付けた。劣化していない件だけを、同じ下書きの三つ組みにした。

- 人間の推敲 ＞ 下書き
- 人間の推敲 ＞ 生成
- 生成 ＞ 下書き

判定に使っている 50 節は、三つ組みの学習側には入れない（分割の heldout として valid に書く）。生成と劣化確認は 379 件すべてに対して行った。

結果（2026-08-14）: 生成漏れなし。人が劣化していないと付けた 378 件、劣化していると付けた 1 件。劣化 1 件は学習側だったので、学習に載る下書きは 328 件（各 3 対）、valid は判定の 50 節すべて（各 3 対）。

```text
make section-middle-gen          # 実施済み
make section-middle-judge        # 実施済み
make section-middle-triples      # 実施済み
make build-section-middle-sentseq-image   # BT 三つ組み文列型 DOK（実施済み）
make build-setwise-section-triples-image  # setwise 修正版 DOK（実施済み）
# 手元スモーク例: DEVICE=cpu SETWISE_EPOCHS=1 make section-middle-setwise
```

**BT 三つ組み文列型**（独立 `s(source,candidate)` + 3 対 BT）の成果物は `outputs/pref-sentseq-section-triples`。既存の `outputs/pref-sentseq-keep*` は上書きしていない。工程 6 の 360 件をこの評価器で採点し直した結果は [RESULTS.md](RESULTS.md)。

**setwise 文列型**（同一下書きについて `{draft, human, Composer}` を 1 回の前向き計算で順位付け。教師順位 human ＞ Composer ＞ draft。損失は ListMLE / Plackett-Luce）の修正版 architecture=`local_stream_then_joint_tokens_v2`（shared local stream encoder 1 layer + joint token encoder 1 layer）で DOK 学習済み。旧 joint-only 版は候補同値崩壊のため不採用。v2b / v2c の数値は [RESULTS.md](RESULTS.md) §8 に記録するが、採否の根拠にしない。

| 項目 | 内容 |
|------|------|
| 教師 | `data/section_middle/pref_{train,valid}.jsonl` を item ごとに 3 行から `{draft,human,Composer}` へ復元 |
| 入力 | source=draft、candidate set={draft,human,Composer}（draft 重複は意図どおり） |
| モデル | 凍結 ruri 文埋め込み + 各 block を shared local Transformer（1 layer）で処理し、全文 token 列を joint Transformer（1 layer）へ。候補 slot/block 位置 embedding は付けない。`meta.json` の architecture=`local_stream_then_joint_tokens_v2` を loader が必須確認 |
| 損失 | full order ListMLE（独立 BT 点 + listwise ではない） |
| valid 指標 | listwise loss、human top-1（strict `>`）、exact order（strict `>`）、human＞Composer、human＞draft、Composer＞draft |
| best | strict human top-1 を第一。tie-break: strict human＞Composer、strict exact order、loss |
| 成果物 | `outputs/pref-setwise-section-triples`（kind=`pref-setwise-section-triples`、architecture=`local_stream_then_joint_tokens_v2`）。学習済み。採点・難試験の本線には使わない |
| 手元スモーク | `DEVICE=cpu SETWISE_EPOCHS=1 make section-middle-setwise`（本学習は DOK） |
| runtime | `scripts/pref_setwise_runtime.py` の `rank_candidates_setwise` |
| v2b/v2c | `make hard-eval-setwise INPUT=... MODEL=...`（`scripts/score_hard_eval_setwise.py`） |

**setwise human-top 比較**（architecture・三つ組み入力・分割・学習設定は full-order 版と同一。損失だけ human を最上位に置き、Composer と draft の相対順位は課さない）は実施済み。不採用。

| 項目 | 内容 |
|------|------|
| 損失 | Plackett-Luce の第1項のみ（`logsumexp([s_h,s_c,s_d]) - s_h`） |
| valid 指標 | human top-1、human＞Composer、human＞draft、human-top loss（比較用に listwise loss / exact order も記録） |
| best | strict human top-1 を第一。tie-break: strict human＞Composer、strict human＞draft、human-top loss。best epoch 16 |
| 成果物 | `outputs/pref-setwise-section-human-top`（kind=`pref-setwise-section-human-top`、loss_mode=`human_top`）。学習済み。採点・難試験の本線には使わない |

| DOK | `make build-setwise-section-human-top-image` → イメージ `pref-setwise-section-human-top:latest`（実施済み） |

結果（2026-08-14）: 学習と同じ三つ組み valid 50 件で human top-1 30/50、human＞Composer 31/50、human＞draft 35/50。いずれも full-order 版（34/50・36/50・41/50）より低い。v2b / v2c の数値は [RESULTS.md](RESULTS.md) §9 に残すが、評価器の採否には使わない。human-top は valid 上では改善ではない。

人間の推敲 ＞ Composer は定義である。劣化確認は Composer を三つ組みの中間に載せるためのフィルタである。

v2 / v2b / v2c の 24 件は、制御改悪（`deg-*`）と旧エンコーダのトークン上限のために節から 3 段落窓を切ったデータである。候補を人間・Fable / Composer・下書きに差し替えたあとも、単位は窓のままである。現行の評価目標（節の下書きに対する人間の推敲と、意味を保った別案）のための試験ではない。採点記録は残すが、評価器の採否・成功指標・学び直しの根拠にしない。次の評価器設計は未決である。

#### 8a. 360 件を開発用教師へ変換（実施済み。質の教師には使わない。いまはやらない）

`make generated-pref-data` で、`data/blind_eval/pairs.jsonl`・`judgments.jsonl`・`items.jsonl` を結合する。

- 左右（A/B）の割り付けを維持し、`preference=a|b|tie` を明示する
- `source_text`（下書き）、`candidate_a` / `candidate_b`、出所、`broken` / `noedit`、`compare_type`、`item_id`、`unit`、`project_id`、`selection_biased` を保持する
- 欠陥ペア・tie を除外しない
- 出力先: `data/generated_pref_experiment/`（原稿本文を含むためリポジトリ外扱い）

#### 8b. item 単位 5-fold 開発評価（実施済み。いまはやらない）

同じ item の 6 比較を分離しない。seed 42 の決定的 5-fold で `folds_section/fold_{0..4}/train.jsonl` と `valid.jsonl` を作る。節 50 item なので、各 fold の valid は 10 item × 6 = 60 件、train は 40 item × 6 = 240 件。fold 間で valid item が重複しないことを検査し、重なれば失敗させる。断片 10 item も同じ分け方で `folds_hunk/` に書くが、8c の学習には入れない。

#### 8c. 節の文列型を、判定 240 件と節ペア学習側 329 件で学習する（実施済み。質の教師には使わない。いまはやらない）

`scripts/train_generated_pref_sentseq.py` が読むデータは次の二つである。

1. **工程 6 の人手判定（節）**  
   `data/generated_pref_experiment/folds_section/fold_{0..4}/train.jsonl`。各 fold 240 件。各件は下書き `source_text`、候補 A/B、人が付けた `preference`（`a` / `b` / `tie`）。6 比較は工程 5 の表と同じ（下書き対生成、生成どうし、人間の推敲対選抜 1 本、人間の推敲対下書き）。同等でない行は、A と B を入れ替えた複製を足す（答えも入れ替える）。

2. **節ペアの学習側 329 件**  
   `data/pref_keep_split_section/train.jsonl`。レビューで採用した下書き対人間の推敲。工程 1 の節ペア 379 件のうち train 329 件だけで、検証側 50 件は入っていない（その 50 件が工程 6 の節 50 item と同一のため）。各件は下書き、人間の推敲、下書きで、ラベルは常に「人間の推敲のほうがよい」。左右入れ替えの複製は足さない。このファイルは CLI では `--anchor-file`（既定はこのパス）。

二つは別ファイルのまま読む。行の印は、判定側が `schema: generated_pref_v1`、329 件側が学習直前に付ける `schema: legacy_anchor_v1`。重み更新は、一度に 64 件（`BATCH_SIZE` の既定）を引いて損失を計算し、重みを直す、を繰り返す。64 件のうち約 16 件（25%、`--anchor-batch-fraction` 既定 0.25）を 329 件側から、約 48 件をその fold の 240 件から取る。そろったあとの損失は同じ BCE である。目標は A なら 1.0、B なら 0.0、同等なら 0.5。329 件は常に「A = 人間の推敲、B = 下書き」なので目標はいつも 1.0。329 件は valid には入れない。

こう分ける理由は件数とラベルである。一つの袋から均等に引くと、329 件のほうが各 fold の 240 件より多く、しかも全部「人間の推敲 ＞ 下書き」なので、更新の大半がその一種類になる。新しく教えたいのは生成文が入った比較と同等であり、それは 240 件側にしかない。329 件は捨てず、毎回の 64 件のうち約 4 分の 1 までに抑える。抑え方は損失の重みではなく、何件引くかである。

そのほかの学習設定:

- 各候補の点数 `r(source, candidate)`、差分 `delta = r(A) - r(B)`
- 文字数特徴の on/off を CLI で切替可能。実験既定は **off**（現行の文列型は文字数特徴ありで、点数と文字数の Spearman 相関 0.932）
- 出力先: `outputs/generated-pref-*`（現行 `outputs/pref-sentseq-keep*` は上書きしない）
- 指標: non-tie accuracy、three-way accuracy、three-way macro recall（a/b/tie）、tie 件数と tie margin 統計、3-way confusion。tie と判定する点数差の閾値は、その fold の判定側 train だけで決め、valid へ適用する。best epoch は valid の three-way macro recall。比較 4・5（`selection_biased`）は指標に使わない
- 起動手順は [DOK-PLAN.md](DOK-PLAN.md)

#### 8d. 独立ブラインド判定（評価器非選抜。段階 5 が検証 50 件で人間の推敲を最上に置けたあと）

新しい下書き・固定生成候補・評価器による選抜を使わない、独立したブラインド判定を別途用意する。ここを通るまで、改善後評価器を本番採点・DPO 教師・Best-of-N 裁定に載せない。

固定した内容（`make freeze-8d-items`。再実行すると seed 42 で同じ 40 件になる）:

- 下書き 40 件。出典は `data/pref_keep_split_hunk/valid.jsonl`。学習 328 件と検証 50 件の三つ組みに使った item は除く。下書きは 100 文字以上。seed 42
- 候補は 2 本。同じ指示文で Composer（`composer-2.5`）が温度 0.7、top_p 0.9、seed 1 と seed 2 で 1 本ずつ出す。評価器が選んだ候補は使わない
- 判定は左右の役割を見せず、下書きと二案を並べて人が a / b / 同等を付ける
- 集計の分母は、人が同等としなかった件。分子は、人が付けた上下と段階 5 の評価器が二案に付けた点の上下が一致した件数

一覧は `data/blind_eval/8d_items.jsonl`、手順は `data/blind_eval/8d_protocol.json`。候補本文の生成は判定の直前に行い、生成後は置き換えない。

#### 8e. 独立評価を通るまで DPO / Best-of-N を止める

現行評価器を報酬にした on-policy 選好学習や Best-of-N 強化は、8d の独立評価が通るまで着手しない。

#### 8 以降（評価器検証後の次段階）

独立評価を通過した新評価器を前提に、次を検討する。

1. **on-policy 選好学習**（DPO 等）: 生成候補の勝敗を新評価器に教師させて推敲 LoRA を更新する
2. **Best-of-N**: 同一入力から N 案を出し、新評価器で最良を採る（`make rank`）

DPO で方針を更新したあとも、同じ報酬モデルを Best-of-N の裁定に使う組み合わせも想定する（詳細は `docs-old/EDIT-MODEL.md`）。

**推敲モデル**の次の一手は、比較 3 の成立・不成立ではなく、三つの率（破壊率・無編集率・改善率）の組み合わせで決める。

- **破壊率が高い場合**: 学習量を増やす再学習を行い、工程 4〜7 を同条件で繰り返す
- **改善率が低く、無編集率が高い場合**: データ見直しを優先する。**8d の独立評価を通過した新評価器がある場合に限り**、DPO や Best-of-N の N 増などを、同じ判定手順を物差しに検討する
- **改善率を主張の中心にできる場合だけ**、「より良くする」実験に進む

## 進め方のルール

- 推敲モデルの判定基準は本書の値で固定し、結果を見てから動かさない
- 評価器には事前の合格ラインを置かず、測定結果を記録して次の測り方・学び直しを決める
- setwise 修正版（full-order）と human-top 版の DOK 学習は済み。v2 / v2b / v2c は評価器の採否に使わない。human-top は学習と同じ三つ組み valid では full-order より悪化しており、その比較では改善ではない。質の評価器の教師は節ペアの三つ組み（human ＞ Composer ＞ draft。Composer 固定）。人間の推敲 ＞ Composer は定義である。工程 6 の 360 件の相対選択と、8a–8c の成果物は質の教師にしない
- 学習設定（指示文・エポック数・評価器の設定）は最適と証明されたものではなく、本計画の固定条件にすぎない。設定違いの比較は、推敲モデルは人手判定の費用がかかるので 1 設定に絞り、評価器は同じ判定データで費用なしに行う
- 生成の比較は、指示文とデコード条件を必ず揃える
- 推敲モデルの成否判断の根拠は人手判定のみとする。**8d の独立評価を通過するまで**、改善前・改善後を問わず評価器を候補選抜・DPO 教師・Best-of-N 裁定に使わない。工程 5 の比較 4・5 で評価器が行った選抜は、当時の探索データとしてのみ扱う
- 原稿本文を含むデータ（生成結果・判定ログ）はリポジトリ外に出さない。Docker イメージは非公開レジストリのみに push する（詳細は [COMMIT-RULES.md](COMMIT-RULES.md)）
