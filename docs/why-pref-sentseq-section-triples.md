# なぜ pref-sentseq-section-triples が最良か

同じアーキテクチャ・同じ 115 万パラメータでも、三つの順位を Bradley–Terry の差として学んだ場合と、人間を 1、他を 0 とする二値分類では結果が分かれています。さらに、旧文列型から直った比較は B で追加した二種類の対と対応していました。ここを中心に結論を組み立てます。

前の考察では、別の点の計算を使う評価器から推測していた。ここでは、同じ文列型の点の計算を使う評価器だけを基準にして見直す。

## 実際に変わったもの

pref-sentseq-keep-pairsplit と pref-sentseq-section-triples は、モデル構造も約 115 万の学習パラメータも同じである。違うのは学習対である。

B では、同じ下書きについて三つの対を作っている。

```{section_middle_utils.py, Lines 120-123}
_pref_row(item=item, pair_kind="gold_vs_draft", candidate_a=gold, candidate_b=draft),
_pref_row(item=item, pair_kind="gold_vs_gen", candidate_a=gold, candidate_b=gen),
_pref_row(item=item, pair_kind="gen_vs_draft", candidate_a=gen, candidate_b=draft),
```

この三つを独立した Bradley–Terry 損失として学ぶ。

```{train_pref_sentseq.py, Lines 475-477}
s_w = model.score_from_doc_vectors_fast(v_src, v_w, len_source=len_s, len_candidate=len_w)
s_l = model.score_from_doc_vectors_fast(v_src, v_l, len_source=len_s, len_candidate=len_l)
loss = torch.nn.functional.softplus(-(s_w - s_l)).mean()
```

同条件の成果物を実測すると、B の検証 50 件は次のようになった。

- A2 の下書き対人間だけで学んだ文列型：人間の推敲＞下書き 50 件、人間の推敲＞Composer 47 件、Composer＞下書き 46 件
- B の三種類の対で学んだ文列型：人間の推敲＞下書き 50 件、人間の推敲＞Composer 47 件、Composer＞下書き 50 件

したがって、B の検証 50 件で明確に増えたのは、Composer を下書きより上に置く件数である。人間の推敲と Composer の件数は増えていない。

なお、BRIEF の 46/50 は、outputs/pref-multigranular/ に複製された batch size 32 の別の重みによる数字である。pref-sentseq-section-triples と同じ batch size 64 の成果物では 47/50 だった。これまでの記録には、二つの重みの混同がある。


## 改善した比較は、B で追加した対と対応している

工程6の360判定で、A2だけの文列型からBの文列型へ替えると、不一致は112件から103件になった。内訳を照合すると、13件を直し、4件を新たに外している。

- 下書きとSFTアダプタの貪欲生成：5件を直し、新たな誤りは0件
- 素のモデルとSFTアダプタの貪欲生成：4件を直し、3件を新たに外した
- 人間の推敲とSFTアダプタの選抜文：4件を直し、1件を新たに外した
- それ以外の三比較：変化なし

下書きと生成の比較が5件だけ改善したことは、Bで追加した「Composer＞下書き」と対応する。

人間の推敲と生成の比較が差し引き3件改善したことは、「人間の推敲＞Composer」と対応する。

Bに直接ない「素のモデル対SFTアダプタ」では、4件を直す一方で3件を外している。ここではほとんど改善していない。

偶然に全体が9件よくなったのではなく、Bで追加した二種類の境界に対応する比較で点の上下が変わっている。

## なぜこの学習方法ではBを利用できたのか

理由は、すでに下書き対人間を正しく学べていた点の計算を変えず、生成文に関する二つの相対関係だけを追加したからである。

この点の計算は、下書きと候補を一組ずつ渡し、文列ベクトルに加えて差、絶対差、コサイン類似度、文字数を線形層へ渡す。学習でも採点でも同じ s(下書き, 候補) を使う。三つの損失は、その同じ点に対して次を直接要求する。

- 人間の推敲の点 − 下書きの点を正にする
- 人間の推敲の点 − Composerの点を正にする
- Composerの点 − 下書きの点を正にする

二値分類では、人間の推敲を1、Composerと下書きを0にする。これは同じアーキテクチャでも、各下書きの中の順位ではなく、全件を共通の0付近で二クラスに分ける問題になる。Composerと下書きの違いも失われる。pref-detect-section が同じ115万パラメータと同じBを使いながら悪かったのは、この目的の違いで説明できる。

三点同時入力では、点の計算自体を変更している。下書きとの差や絶対差を明示的に渡さず、候補間の注意から関係を学ばせている。その結果、Bで直接教えた人間の推敲＞下書きさえ41/50まで落ちた。Bの内容ではなく、既に成立していた点の計算を捨てたことが問題だったと読める。


## 改善の限界

人間が人間の推敲と判定できた件だけを見ると、同じ文列型で次のように変わった。

Bの検証50件中の43件：判定できなかった数は3件から2件
工程6の60件中の49件：判定できなかった数は29件から25件
改善はあるが、前者は1件、後者は4件である。近い書き換えを見分ける問題はまだ解けていない。

また、スコアと文字数の相関は0.932から0.940へ上がっている。一般的な文章の質をより正確に捉えた、あるいは文字数への依存が減った、とは読めない。

さらに、pref-sentseq-section-triples はBの検証150対の正解率で4 epoch目を選んでいる。その検証50件を後から人が判定しているため、43件中2件という数字は、未知の下書きへの独立した成績ではない。

現時点で根拠を持って言えるのは、次である。

pref-sentseq-section-triples は、既に下書き対人間を学べていた文列型を保ったまま、Composerを下書きと人間の推敲の間に置く二種類の相対制約を追加した。その制約に対応する生成文の比較が実際に改善した。B全体から一般的な質の表現を獲得した、とまでは言えない。

一点だけ限定する。生成文を含む比較で改善が集中したことは、B の追加対が関与した証拠だが、どちらの対が何件を直したかまでは確定できない。B の検証でも人間対 Composer は2件改善し、別の2件が悪化して、合計は47件のままだった。

したがって、正確な結論は「三種類の対を独立した Bradley–Terry 損失で学ぶ方式が改善を生んだ」までである。人間対 Composer と Composer 対下書きの寄与分離には、対種別のアブレーションが要る。
